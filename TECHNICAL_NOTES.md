# Technical notes

## Switch 2 launch compatibility

The checked PokeDinner 2.0.0 loader performs early Switch 2 detection using a `main.npdm` in the opened file's containing directory, before parsing the container's embedded ExeFS. With default settings and no companion, it selected the Switch 1 memory layout and clock and boot failures were observed. A user subsequently reported booting without the companion after selecting 12 GiB RAM; the earlier manual-test profile was also set to 12 GiB. Memory configuration can therefore bypass the observed boot failure without changing the embedded metadata. Compatibility with every game/build and correct runtime timing are not established by that boot report.

Version 2.0 includes an optional reversible Windows x64 emulator patch that reads the embedded NPDM before mode selection. Supported patched loaders no longer require an external companion; real-startup checks match the external-file path's 31.25 MHz timer. This does not establish universal gameplay or FPS compatibility. See [EMULATOR_PATCH.md](EMULATOR_PATCH.md).

Version 1.4.3 enables package-folder output by default. Unchecking the option saves only the XCI/NSP. Package-folder output copies the exact snapshot NPDM beside the package and records its hash in a local JSON report. It remains an early-detection workaround, rather than a universal requirement. Conflicting or concurrently created companions are preserved. Verification remains enabled independently of whether a report is written.

A GUI-only startup caution describes the 12 GiB setting and experimental status. Dismissal is opt-in, versioned by notice content and stored in the application's local preferences. No emulator configuration is changed by opening or dismissing the caution.

Generated NACP uses ApparentPlatform at `0x3217` (1 for Switch 2) and application-error prefix at `0x3214` (3 for Switch 2). TitlesDataFormat is read at `0x3215`; compressed title bytes are preserved. Earlier releases used incorrect `0x323D`/`0x323F` offsets. The loader's early NPDM check was the decisive launch failure in the checked build.

Explicit compatibility setup adds missing locally generated plaintext placeholders to the chosen profile. It never exports existing values, preserves `prod.keys`, validates existing entries, and backs up an existing autogenerated file before appending. It does not supply retail decryption keys. Scanning/building never run setup automatically.

Loader reference: https://git.eden-emu.dev/Franseven/PokeDinner-a-Eglantine-Fork/src/branch/master/src/core/core.cpp (`IsSwitch2Program`). Format reference: https://switchbrew.org/wiki/NACP .

## Artwork pipeline

`ArtworkSelection` stores a source path and normalized crop coordinates, or a fit-whole-image mode. Files are opened with Pillow, limited to 50 megapixels, EXIF-oriented, and converted to RGBA using the first frame/page. A centered square is used by default. Crop coordinates are checked for finite, in-range values and a square region at least one source pixel wide. Crops are resampled to 256×256 with Lanczos and encoded as JPEG; transparency is composited over white. Original files are not modified.

The modal editor pans/zooms in source-image coordinates. The canvas and icon preview are separate from the immutable source. A reduced preview source is cached for responsive dragging; the full source is used when the final icon is encoded. Cancel leaves the previous selection unchanged. Supported image codecs are bundled with Pillow, including WEBP, AVIF, ICO and ICNS; no new runtime dependency was added.

The Paste button and Ctrl+V explicitly invoke Pillow's Windows clipboard reader. It accepts bitmap data and artwork file lists; a plain local image path is also supported. Bitmap data is saved under an app-owned temporary directory and removed on close. Ordinary text-editor pastes are preserved; clipboard reads are not polled or performed on startup. Native shell drop dispatch shares the same extended artwork extension list as the picker. Clipboard adapters are tested with synthetic mocked data rather than reading a user's live clipboard in the automated suite.

## Interface and motion

The 1.1 interface retains the original packaging workflows, using native Tk text editors inside rounded shells. Original icon paths and surfaces are rasterized at 3–4 times their final resolution, then downsampled with Lanczos filtering to avoid jagged edges. No AI-generated or Nintendo artwork is used for the interface.

Hover, entrance, artwork reveal, status color and progress transitions use elapsed time with cubic easing, scheduled on the Tk UI thread. Work stays on the background build thread. Motion follows the Windows client-area animation preference; there is no visible animations toggle. The layout contracts at the minimum supported window size while keeping controls visible.

Windows folder/artwork drag-and-drop uses `DragAcceptFiles`, `WM_DROPFILES` and `DragQueryFileW`. A window procedure is installed only on the app's own top-level window and restored before it closes. Shell drop data is released with `DragFinish`; no system permissions or Explorer settings are changed. Browsing and manual path entry remain available.

References: https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-dragacceptfiles and https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-dragqueryfilew .

## Container construction

The program is a Python implementation written for this packaging workflow. It does not invoke hacPack or NSC Builder. Nintendo Switch format documentation and publicly available Eglantine loader code were consulted for interoperability; their C/C++ source is not bundled in this app.

1. Scan a selected folder to a bounded depth for sibling `exefs` and `romfs` folders. Read the application ID from NPDM's ACI0 block. Offer complete-looking candidates as separate snapshots, sorted by numeric folder version. Exclude explicit DLC/AOC folders.
2. Encode ExeFS as PFS0 with hierarchical SHA-256 hashes. Encode RomFS directory/file tables, hash buckets and aligned file data.
3. Build a six-level RomFS IVFC tree with 16 KiB blocks. Wrap ExeFS and RomFS in a Program NCA.
4. Preserve available standard control metadata or create basic NACP data; embed supplied artwork and generate a Control NCA.
5. Generate an Application CNMT referencing the complete Program and Control NCAs by SHA-256, content ID and size, then place it in a Meta NCA.
6. For XCI, pack the NCAs in the secure HFS0 partition, with empty update/normal partitions and a trimmed legacy-compatible HEAD header. For NSP, pack the three NCAs directly in PFS0. NCA distribution is GameCard (1) for XCI and Download (0) for NSP, set before calculating content IDs and CNMT records. The numeric snapshot version is recorded in the generated Application CNMT; the result is not a set of original base/patch NCAs.

NCA signatures are empty. NCA headers and sections are plaintext. Rights IDs are absent. Actual Nintendo encryption keys, gamecard certificates, RSA signatures and challenge-response data are neither recovered nor generated. This is an **emulator repack**, not an authenticated Switch 2 cartridge backup or a format suitable for a retail console/flashcart.

## Verification

The independent reader recognizes XCI/HEAD with HFS0 or NSP/PFS0 and validates the wrapper, NCA distribution type, all complete NCA hashes, filesystem section header hashes, hierarchical SHA-256 blocks, all six IVFC levels, CNMT records and digest, and program ID. XCI additionally checks its HFS0/header hashes. It parses the packed ExeFS/RomFS and compares every source file's SHA-256 and filename to the result. Expected source hashes are captured from the actual bytes streamed into the output, avoiding another input read during verification. Standalone verification without supplied hashes still reads the originals. File size and modification time are checked again before committing either format.

A bounded mmap-range abstraction avoids copying whole multi-gigabyte files into memory and closes the mapping on cancellation/error. Large data is streamed; memory grows principally with RomFS tables and the bottom IVFC hash table, roughly 2 MB per GB of game data, plus runtime/buffers.

Version 1.3 uses scoped memoryviews for output hashing, reuses each complete NCA digest for CNMT verification, and computes RomFS sibling links once in linear time instead of repeatedly searching each directory. Directory enumeration reuses cached `DirEntry` metadata; RomFS file parts retain known sizes rather than statting all paths again. Large file counts still require per-file opens during integrity-tree creation, content hashing and writing, plus the final metadata check. No verification layer has been disabled. Stage timings in the report help identify disk versus metadata costs; percentages are stage estimates, not elapsed-time predictions.

## NSP and conversion efficiency

NSP output is implemented directly on the shared pipeline: it streams the Program/Control/Meta NCA blobs into PFS0 rather than constructing or reading back a temporary XCI. There is no intermediate NCA file either. Source payloads, artwork, integrity trees and metadata use the same construction code for both formats. The format changes distribution metadata and thus NCA hashes/content IDs, but not the original game payloads. A regression check confirms NSP performs no more source-file opens than XCI on the same fixture and writes no intermediate XCI.

An NSP saves only small wrapper overhead compared with this app's trimmed XCI, rather than compressing the game. Changing wrappers does not improve gameplay speed or eliminate the costly filesystem/hash work. Tickets and certificates are omitted because the generated content has no rights ID and is plaintext. This relies on the compatible emulator's loader; retail-console installation is not supported. Separate base/patch/DLC reconstruction remains a different task from packaging one complete snapshot. Existing encrypted XCI/NSP conversion and compressed NSZ/XCZ output are not implemented.

References: https://github.com/DarkMatterCore/hacPack and the XCI/NCA references below.

The output is written to a unique `.partial` file and renamed only after the selected checks finish. Existing output files are refused. Concurrent changes to source size/mtime cause failure. This is not a filesystem snapshot mechanism; keep the input idle while building. Windows rename behavior is relied upon to refuse a destination created during a build.

## Scope and known limitations

- Single application/program and a complete mounted snapshot only. No automatic base/update overlay, BKTR patch application or DLC registration.
- The scanner cannot prove an update's RomFS is complete. A structurally valid package can still contain an incomplete source dump.
- A source `control.nacp` is sought only at conventional root/control locations. Compressed title strings in an existing NACP are retained rather than rewritten; the visible custom title may therefore remain unchanged in that case.
- Generated NACP has basic title/platform/version identifiers; original save configuration and service settings cannot be recovered from ExeFS/RomFS alone.
- No original SDK version can be reliably inferred for all dumps. Generated NCAs use a fixed loader-compatible SDK field (`0x000c1100`); this is not asserted to be the original game's SDK version.
- Up to 32 GiB per package; XCI follows the implemented legacy capacity enumeration. Larger packages are not a supported release target.
- Symbolic links and Windows reparse points within input trees are refused. ExeFS must be flat. Very large RomFS metadata tables remain subject to the format's 32-bit offsets.
- Paths and original payload hashes are stored only in the local output report. Reports are not automatically uploaded.
- Packaging does not supply CPU/GPU/service emulation, fix gameplay, or establish compatibility with every game, emulator, or Eglantine fork.
- Portable EXE is Windows x64. Running the source on another OS is not a supported release target; in particular, overwrite behavior must be reviewed before porting.
